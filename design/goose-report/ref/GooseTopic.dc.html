What happens between a hook firing and a peep changing state?

asked by the owner · answered from 8 files in 4 areas

In short

Claude Code posts the hook to a loopback port. The server matches it to a session by sessionId, one pure function works out the new state, and the whole list is pushed to the window, which only redraws.

1 · The hook posts

The integration install adds one entry per hook to ~/.claude/settings.json. Each entry posts the hook's JSON to the widget's port on 127.0.0.1. Nothing is read back, so a slow widget can never hold Claude Code up.

2 · The server finds the session

server.rs accepts the post and hands it to the Claude source, which parses the payload and pulls out sessionId. If no session file has been seen for that id yet, the event is held until the sessions directory catches up.

3 · One function decides

state.rs takes the session's current state and the event and returns the next state. PreToolUse gives working, the matching PostToolUse gives thinking, Notification gives waiting, Stop gives success. It reads no clock and no files, which is why every transition has a test.

4 · The snapshot goes out

The backend emits the full session list as one sessions event. The frontend does not patch anything: rows.ts sorts attention states first and rowView.ts sets el.state on the row's peep, which is the only line that touches the art.

5 · Where it can go wrong

Three places. A session started before the hooks were installed sends nothing, so it falls back to the transcript tail and lags by a second or two. A busy session with no event for 6 minutes is marked stuck by a timer, not by a hook. And a hook that arrives for a dead PID is dropped.

Read first

state.rs, then its tests. The rest is plumbing around that one function.

Where do poll results get cached?

asked by the owner · answered from 3 files in 2 areas

In short

Nowhere yet. Every request for results counts the votes again.

api/results.ts runs one COUNT query per poll against the votes table each time it is called, and returns the totals as they are. There is no cache in the API, no cache header on the response, and the page does not keep the last answer.

That is fine at today's size. If it becomes slow, the one place to add a cache is api/results.ts, keyed by poll id and cleared when a vote is written.

Files involved

  • api/results.tscounts votes on every call
  • db/votes.sqlthe table it reads
  • web/ResultCard.tsxfetches on every mount
